# 浏览器 Agent 性能优化

## 0.1.167：平台固定流程先执行，异常才启动导航 Agent

猎聘和 BOSS 各自的驱动直接执行职位选择、卡片定位、打开简历、读取、返回、翻页及已授权招呼。正常页面不先调用导航模型；模型调用只保留职位要求提炼、列表初筛和详情匹配评估。固定目标不存在、歧义或状态改变时才启动通用导航，处理后由宿主自动接回同一驱动。未知输入结果与持久化失败不进入恢复。已适配平台的导航恢复上限为 8 轮。

固定流程默认使用 DOM 视口，直接复用动作返回的 DOM；同一快照的卡片解析结果复用，评估之后仍显式更新操作引用。推进列表复用已读卡片，稳定人选标识连续不变时有界交回，不再靠全页数量、在线提示或滚动坐标判断已翻页。同任务内相同原文、姓名、评估阶段、要求和筛选可复用已核验判断；原文或要求改变即重新评估。

`sourcing.fast_execution_finished` 分开记录 `navigationTurns` 与 `assessmentTurns`，正常路径应为前者 0。本轮 503 项本地测试通过；登录猎聘页面只读核验定位到 3 张卡片，快照约 239 ms、首次固定解析约 49 ms，同快照再次读取没有新增浏览器调用或模型调用。这只验证定位和复用，不代表完整招呼或整轮耗时。BOSS 完整实账号流程尚未验收。

## 0.1.163：同一导航会话与结构化动作观察

人才寻聘由一个导航 Agent 持续推进。平台现有流程作为 `sourcing_collect` 业务工具连续调用浏览器、初筛、详情评估、保存和已授权招呼；页面差异返回当前观察与宿主状态，由原对话处理，再明确调用业务工具继续。评估器只接收归属已核验的不可变原文，不具有浏览器能力。刷新引用但未改变页面不能重新启动失败路径；结果未知或持久化失败仍立即停止。

普通导航不再要求命中网站按钮白名单，也不为每次点击扫描全部搜索控件；模型根据当前语义选择目标，真实输入继续由浏览器核对引用、文档与命中。职位和筛选确认、推荐/搜索来源、明确的候选人入口、已选人归属、招呼授权、去重及间隔保护保留。

模型默认接收紧凑语义树，完整当前观察留在宿主，可按引用分页或检索续读。初始观察不再任意截到 6000 字符，新观察到达后统一压缩过期首屏、恢复观察和普通工具快照。支持观察格式的扩展直接返回所需快照；旧扩展只执行条件等待，随后补一次语义观察，避免生成一份不用的 DOM 快照。显式 `returnSnapshot=none` 与观察格式继续生效。

输入结果可附带 `effects`：新快照 ID、URL 是否变化、可唯一关联的目标新引用、新出现的控件及前景弹窗。它们只证明观察到的界面状态，不证明消息送达。观察补读失败保留原输入回执，禁止自动重放。原生多工具分组与顺序执行继续沿用。

导航输出上限为 2048 token；评估沿用独立预算。成功取得的模型元数据在同一任务 runner 内缓存 5 分钟。`browser_agent.model_turn` 增加 `modelPurpose`、`maxOutputTokens`、`cacheReadTokens`、`cacheWriteTokens`、`reasoningTokens`；`browser_agent.browser_call` 记录 `preflightMs`、`remoteMs`、`waitedMs` 和是否附带快照。缓存 token 以提供方实际返回为准，不代表本地强制开启了缓存。

本版同时兼容真实详情读取校验：列表摘要、刷新后的列表和只有摘要的弹窗不计入采集人数；必须取得当前候选人的前景或独立详情经历，才允许详细评估和保存。旧版已存摘要不再阻止后续获取真实详情，招呼历史仍单独核对。

本地构建、类型、模拟模型及传输回归用于验证上述调用组织和保护条件，尚未证明真实账号同任务提速幅度。未修改薪招扩展或网关链路；真实猎聘/BOSS 的完成率和速度需安装后使用相同职位、人数与模型对比。

## 0.1.107：来源职位核验是无解条件（用真实页面契约修正）

来源：用户反馈「打招呼任务成功了，简历入库任务失败了」，任务 `bd87be56-c5ac-42fb-8d7e-decf140c5b9e`（liepin，limit=3），24.7 秒以 `PRESET_NO_PROGRESS` 止损。**本轮是第一次不再靠推断修 bug**：按技能规范接管浏览器执行权，对真实页面做只读快照，直接读出契约。

- 好消息：0.1.106 全部生效——模型 7 轮全部正常（1.8–4.0s/轮，无 `MODEL_FAILED`），预设越过了 `foreground_present`，并在 24.7 秒（而非 7 分钟）止损。
- **实测契约**（`lpt.liepin.com/resume/apply` 只读快照）：

  ```
  ref_143  div       name="全部职位"   bounds{188,70,180,32}   parentRef=ref_392
    └ ref_21 combobox input  elementId="ejobId"  value=""  parentRef=ref_143
             DOM 快照 states=[enabled, editable, collapsed, occluded]
             语义(AX)快照 states=[occluded]        ← 没有 collapsed，也不给 value
  ```
  来源职位是 rc-select：**可见文案挂在容器 div 上，值所在的是一个空的 search input**。
- **根因：核验条件无解。** `selectedResumePosition` 原来只检查被引用的那一个元素，且要求 combobox 带 `collapsed`。而证据跨两个元素：指向 input 时 AX 快照没有 `collapsed`；指向容器时 `role !== 'combobox'` 直接返回 false。**没有任何 ref 能同时满足**，模型 3 次 `task_confirm_source_position` 全部 `RESUME_SOURCE_POSITION_UNVERIFIED`。
  - 修正：新增容器形态——容器自身文案命中期望值、且它包含一个**未展开**的下拉控件时通过；同时去掉对 `collapsed` 的硬要求（展开态仍然一律拒绝）。
  - 优先级：直接控件证据优先，容器仅在无控件证据时兜底，避免同一筛选同时命中容器与 input 造成歧义。
  - 面板给的既有安全属性保留：下拉展开时容器文案可能只是刚输入的关键词或展开的选项列表，一律不作为已选证据（该用例是 0.1.x 既有回归，本次修改先撞到它，说明回归网有效）。
  - `task_confirm_source_position` 的 `ref` 改为可选：强制模型只引一个元素正是这条核验无解的原因。
- 本地回归 273/273 通过（新增 1 项，直接以实测快照的 DOM/AX 两种形态作为夹具）。

## 0.1.106：宿主种子不再伪造 assistant 轮次（思考模式契约）

来源：用户以 0.1.105 实机跑 `taskId=665ea865-1aca-4228-bf13-3b8335cca4f1`（liepin，limit=5）。**0.1.105 的两处修复都生效**：`browser_click` 成功执行（`outcome=succeeded`、`requestedRef=ref_25`、`targetRole=tab`、`point={x:1122.99,y:78}`），预设随后以 `unrecognized_state` 正常交棒；模型失败的**真实原因**也被 0.1.105 新增的日志完整带出：

```
INVALID_REQUEST HTTP 400
The `content[].thinking` in the thinking mode must be passed back to the API.
```

- **根因：宿主预设的执行结果被伪造成 assistant 轮次。** `runBrowserAgent` 把 `initialToolResults` / `beforeTurn` 的种子渲染成「一条只有 tool-call 的 assistant 消息 + 工具结果」，作为模型的起始上下文。思考模式下服务端要求：带工具调用的 assistant 消息必须附回它自己的 thinking。而种子不是模型产生的、根本没有 thinking，于是**每轮请求在 turn 1 就被 400 拒绝**，且与页面状态无关。
  - 修正：宿主种子改为 **user 轮次的「宿主事实」观察清单**（含工具名、参数与结果，并声明"不是你的输出、不要原样重放"）。语义不变，对是否开启思考都成立；单条结果渲染上限 6000 字符，整批仍受既有分组压缩与上下文预算约束。
  - 反向验证：新增回归确认**真实**模型轮次的 `reasoning` 块会原样回传到下一次请求（`assembler.blocks()` 全量透传，压缩只作用于观察结果、不触碰 assistant 轮次），所以被拒的只有伪造轮次。
- **排障链路闭环**：0.1.105 加的两项观测（`failedDetail`、`failureCode/status/message`）本轮各自发挥作用——预设停在哪个工具、模型为何失败都一次看清，没有再出现"只有错误码"的情况。
- 本地回归 272/272 通过（新增 2 项：宿主种子必须以 user 轮次出现且不得伪造 assistant 轮次、模型思考内容必须回传）。

## 0.1.105：同类参数事故的第二例 + 模型失败原因不再被吞

来源：用户以 0.1.104 实机跑 `taskId=b8189328-be87-462c-acd0-5dec10568770`（liepin，limit=2），2066ms 结束。日志显示 **0.1.104 的 `browser_wait` 修复生效了**：预设越过了加载等待，语义快照 `coverage.nextOffset=600`（扩展分页能力确认可用），并在语义截断后回退 DOM 快照，然后停在 `failedTool=browser_click` / `errorCode=BROWSER_ARGUMENT_INVALID`。

- **根因一：`frameId` 被带给不接受它的工具。** 扩展的快照输出**始终带 `frameId`**（顶层为 0）。预设的 `input()` / `reveal()` 只要 `page.frameId !== undefined` 就原样带上，于是 `browser_click` / `browser_hover` / `browser_scroll` 全部携带 `frameId: 0`；而网关只有 `browser_snapshot`、`browser_list_frames` 等少数工具声明了 `frameId`，`additionalProperties:false` 直接拒绝。因为顶层帧也带 `frameId: 0`，**首屏之后的第一次点击必然失败**。
  - 修正一：预设只在「非顶层帧且目标工具声明了 frameId」时携带它。
  - 修正二（防复发）：`AgentBrowserTools` 对未声明 `frameId` 的工具剥离该字段。这不改变行为——交互类能力从快照记录取帧，且扩展对非顶层帧的交互本就明确拒绝（`FRAME_INTERACTION_UNSUPPORTED`），命令里的 `frameId` 不参与解析。
- **根因二：模型失败的真实原因被吞掉。** 上一版新增的日志已指认 `finishKind: "error"`。适配层会把抛出的失败规范成终止 finish 块并带上提供方事实（`code`/`status`/`message`），而原实现只判断「不是 stop/tool-calls」就结束任务，完全丢弃了原因；同时因为 `chunks > 0` 连重试都没触发。
  - 修正：解析 `finish.failure`，日志记录 `failureCode`/`failureStatus`/`failureMessage`/`providerRetryAfterMs`；任务结果直接给出真实原因（`BROWSER_AGENT_MODEL_FAILED: <code> HTTP <status> <message>`）；提供方失败在同一轮内有界重试一次，**用户/宿主取消（`aborted`）不重试**。
- **排障能力**：`recruitment.preset_paused` 新增 `failedDetail`，记录参数校验失败的字段路径与规则。本次连续两轮只看到 `BROWSER_ARGUMENT_INVALID` 却不知道是哪个参数，就是缺这个字段。
- **测试保真度**：替身此前既缺 `frameId`，又把 `browser_snapshot` 声明为不含 `frameId`，与真实扩展/网关不符，因此这类事故在回归里测不出来。现已按真实行为补齐，并断言 `browser_click`/`browser_hover`/`browser_scroll` 绝不携带 `frameId`。
- 本地回归 270/270 通过（新增 3 项：frameId 按声明保留/剥离、提供方失败原因可见且有界重试、取消不重试）。

## 0.1.104：修正「预设每次都在 2 秒内交棒」的真正根因

来源：用户以 0.1.103 实机跑 `taskId=39053cd9-25c2-4eea-969e-ebb8a8f86fb3`（liepin，limit=2）。任务 2.7 秒结束，`turns=1`、`sent=0`，结果 `BROWSER_AGENT_MODEL_INCOMPLETE`。日志里只有一个 `recruitment.preset_paused`：`reason=tool_failed`、`failedTool=browser_wait`、`errorCode=BROWSER_ARGUMENT_INVALID`。

- **根因一：`browser_wait` 被传了 `purpose`。** 网关的 `MUTATION_CAPABILITIES` 不含 `browser.wait`，所以该工具是只读能力、schema 里没有 `purpose`；而 `AgentBrowserTools` 只给写工具注入 `purpose`。预设却给加载等待传了 `purpose: 'navigation'`，`additionalProperties:false` 直接拒绝 → 预设 `tool_failed` → 交棒。新开标签页首屏必定是空的，预设必定走这一步，所以**每一次打招呼都在 2 秒内交棒**。这是长期存在、此前被误判为「职位核验过严」的问题：0.1.103 的日志显示预设根本没走到职位核验。
  - 修正一：预设不再对 `browser_wait` 传 `purpose`。
  - 修正二（防复发）：`AgentBrowserTools` 对只读工具直接剥离 `purpose`。它是宿主元数据、不是网关字段，不该让整个任务因校验失败而中止。写工具的严格校验不变。
  - 测试保真度也修了：`test/recruitment-presets.test.mjs` 的替身把 `browser_wait` 声明为写工具，与真实网关不符，因此这套替身一直没抓到该缺陷；现已按真实能力标注为只读，并断言加载等待不得出现 `BROWSER_ARGUMENT_INVALID` / `failedTool=browser_wait`。
- **根因二：模型流空转即判死。** `BROWSER_AGENT_MODEL_INCOMPLETE` 在交棒后 185ms 出现，`turns=1`、零 token 产出，且没有 `model_failed`——说明流是「正常结束但没有 finish」，而不是抛异常。原实现只要 `!finished` 或 finish kind 不是 stop/tool-calls 就直接结束整个任务。
  - 修正：一整轮**零 chunk** 时在同一轮内重试一次（有界，最多 2 次尝试）；只要有 chunk 就不重试，避免重复生成。新增 `browser_agent.model_incomplete` 日志，记录 `chunks`、`finished`、`finishKind`、`firstChunkMs`，下次复现可直接定位是提供方空流还是别的原因。
- 本地回归 267/267 通过（新增 4 项：只读工具剥离 purpose、写工具仍拒绝未知字段、空流重试一次、持续无 finish 有界停止）。
- **未验证**：根因二的确切原因尚未证实（本次无法复现提供方空流）。需要实机复跑；若再次出现，`browser_agent.model_incomplete` 会给出判定依据。

## 0.1.103：解死局 + 稳定身份止损

来源：用户 2026-10-16 提供的真实猎聘打招呼时间日志（23:05:26 预设交棒，23:12:32 才因 `BROWSER_AGENT_REPEATED_FAILURE` 中止，约 7 分钟 0 人）。对照参考项目 `超前浏览器AI助手-v0.2.0` 的执行形态后，先修「快路径进不去」，再修「进去了也要止损快」。完整问题清单与后续阶段见 [提速与卡死治理路线图](browser-agent-speedup-plan.md)。

- **职位核验分级**（`position-evidence.ts`）：`exact` / `degraded` 两级，用返回值区分而非只抛错。降级条件收紧为：目标名称在平台关联列表里唯一 + 页面上只有一个带该名称的选中条目 + **页面上没有出现过可对照的职位 ID**。元素暴露了 ID 却对不上时仍然拒绝，不会因为「名称对」就放行。降级通过写入 `recruitment.position_evidence`，可事后审计。
- **读得到当前职位**：候选发现放宽到「原文提到目标职位名」的普通文本节点（不再要求 AX `selected` 状态或 button/combobox 角色）。未选中的选项/标签一律排除；普通文本节点仅在页面唯一提及时才可能通过，避免标题、推荐位被当成当前职位。
- **同名职位不再空转**：名称候选与 ID 候选分离。能用平台职位 ID 唯一确定才点；用户显式指定的 `selectedPlatformJob` 优先；多个同名又没有 ID 证据时立即以 `PRESET_POSITION_AMBIGUOUS` 停止并说明原因，不再交给模型试。城市/薪资自动消歧待确认 `jobAds` 是否返回该字段。
- **下拉触发器兜底**：按稳定身份记住已 hover 过的触发器，第二次仍未展开时改用一次真实 click，而不是重复 hover 或直接交棒。
- **停滞收敛**：连续 3 次相同原因且页面身份没有变化即 `PRESET_NO_PROGRESS` 停止。只有 `position_unverified` / `repeated_step` 计入；搜索准备、`unrecognized_state`、`tool_failed` 这些本该由模型多轮处理的状态不计入，避免误杀。
- **稳定失败身份**：`failureKey` 去掉 `bounds` 与 `states`。面板一开一合、滚动一像素、焦点切换不再清零计数——这是本次空转要 7 分钟才止损的直接原因。为保持既有语义，**失败阈值仍为 3 次**，靠稳定键让三次更快到达。
- **预设签名收敛**：`attempted` 与停滞计数不再哈希整页 items，改用页面身份 + 元素数量 + 目标身份 + 业务状态，无关文案（时间戳、活跃度）不再让同一步骤被反复执行。
- **已失败做法账本**：失败过的做法在下一轮明确列给模型（工具 + 目标标识 + 错误码）。目标标识只用 role 与 elementId，不含页面文案，否则会把已压缩的旧快照正文重新灌回上下文。
- **进度来源标记**：模型自述带 `source: 'model'`，与宿主工具级事实分开。新增 `browser_agent.model_narration`，只记轮次与字符数，不记正文（遵守开发日志不保存模型回复的既有约定）。
- **保护路径标注**：任务路径与会话路径两套重试保护的停止原因分别标注来源，便于排障时区分；语义未统一。
- 本地回归 263/263 通过（新增 10 项：职位降级/Hover 展开/click 兜底/同名立即停止/显式指定平台职位/有限收敛/ID 对不上永不降级/ticking 页面不能延长停滞/失败身份跨 ref 稳定/证伪账本与进度来源）。**这是替身回归，不是实机测速**；真实账号上的预设命中率与耗时仍需实机验收。
- 本版未修改薪招扩展，未改 `browser-execute-actions` 批量路径；快照分页依赖扩展侧未提交改动发版。

代码和回归复现确认：选人只是建立记录，却把姓名和辅助文字当作必须可点击的元素检查。可读但 disabled/occluded 的辅助节点会阻断选择。日志未保留完整现场节点，不能据此断言当时一定是扩展遮罩、子节点命中或页面弹窗；也没有证据表明上传接口被本次优化改坏。

### 修复与提速

- 身份识别使用可读证据，不再要求全部文字都可点击；hidden/invisible/blocked_by_dialog 仍不可作为当前身份。附件入口及真正的输入仍须通过动作检查，未知采集/入库不自动重放。
- 足以建立旧身份键的快照不再逐个补查节点；缺失关联或需要补充身份上下文时仍检查，保留历史去重键兼容。只读补查结果仅在同一快照复用；附件动作前的检查不复用。
- 开始时直接读取 tabs，在已有明确授权标签页时读取快照，再交给第一轮模型；多个候选标签页且无明确选择时不擅自导航。省掉让模型分别指挥这些确定只读步骤的往返。
- navigate/open/history/scroll/wait 成功后直接附带一次页面观察；若观察失败，保留原动作回执并明确要求重读，绝不重放原动作。继续保留 0.1.91 的输入后观察及历史快照压缩。
- 选人和导入等宿主工具也能在明确过期引用错误时返回只读恢复结果。同一目标/错误的重复失败计数不再因重新生成 snapshot/ref 而归零；失败后停止，不把“更早停止”统计成“成功提速”。
- 首屏沿用有界完整观察，不强制截为前 120 个节点；仍可本地续读，避免候选人在列表后方时反而增加模型轮次。
- 取消简历任务后，最多用 2 秒只读等待原在途命令收尾；确认仍是自己持有且空闲后才结束一次。其他本地任务或 remote owner 不释放，忙超时不强制结束。保留 begin/finish 原始结构化错误码，避免统称 TOOL_ERROR。

### 浏览器任务专用模型配置

在插件配置中新增以下可选字段（见 `examples/config.patch.yml`），不改变全局默认模型或保存新的凭据：

```yaml
browserAgentReasoningEffort: auto-low
browserAgentProvider: ''
browserAgentModel: ''
```

`auto-low` 只在宿主模型元数据明确声明支持 `low` 时使用；否则继承当前档位。元数据查找每个任务一次、最多 1.5 秒，不是每一步查询。`inherit` 不查询元数据且完全沿用所选路由档位；明确指定不支持的档位会停止，不发送猜测参数。provider/model 留空沿用默认模型；需要专用模型时两项一起填写宿主已配置的 ID。专用路由不继承另一个默认模型的推理档位。实际选择记录于 `browser_agent.model_profile`，不得把“设置了 auto-low”当作服务实际启用了 low。

当前日志中的路由是 `xinling-workbuddy / glm-5.3-flash`。若服务首内容就需要数秒，减少浏览器传输无法消除这段等待。要进一步比较模型服务，应保持页面与任务一致，查看 firstContentMs、generationMs、模型轮数、实际成功人数。

### 与 v0.2.0 的比较边界

依照 reverse-engineer-anything 技能尝试检查工具环境；专用逆向服务不可用，采用本地打包 `background.js` 与已有 recovered 源码静态核对，未改工具配置或执行参考扩展。其循环同样等待远程 provider.sendChat，再执行工具；支持工具批处理和 provider 推理参数。这不等于模型运行在浏览器内部，也不能证明只因少一层网关就快数倍。这里借鉴的是减少模型往返的执行组织，未复制招聘平台选择器或降低业务写入校验。

## 0.1.91：模型往返与历史观察优化（历史记录）

本次在 0.1.90 的共享原生工具循环上做增量优化，打招呼与简历采集共用；不改变宿主默认模型/供应商/推理档位，不改网关传输和薪招扩展，不安装或重载用户客户端。此前 0.1.88 的历史耗时不能直接当作本版本的对照测速。

## 已实现

- 支持 `observe` 的写工具在模型未显式指定时使用 `dom_quiet + viewport`，观察上限 2500 ms，`requireChange=false`。输入后顺带返回新快照，省去“让模型再调用 snapshot”的往返。页面安静不等于业务成功，仍须由业务 hooks 核实证据。显式 `observe` 原样保留；同轮后续输入仍依赖旧引用时，可指定 `returnSnapshot=none`。
- 观察超时保留原输入回执，不重试写入。`verification.snapshotStale=true` 的快照不进入可操作缓存、不向模型提供可用引用，须另行观察。
- `SNAPSHOT_EXPIRED / PAGE_CHANGED / ELEMENT_NOT_FOUND` 的明确引用错误可带回一次只读新快照，仍经过原来的 schema、来源域与业务前置检查。原动作不重放；后续操作由模型根据新证据决定。结果未知的写入先终止，不进入恢复。
- 每个标签页/框架的最近两个不同快照保留正文，较早快照正文替换为历史标记；原工具调用、对应结果、操作回执均保留。同版本的续读切片保留，避免丢掉刚补读的信息。完整当前页仍在 broker 缓存中，可用 `browser_read_observation` 续读。
- 同工具、同参数、同错误累计三次且期间未成功则停止空转；参数键顺序不同不绕过计数。新参数仍可尝试，成功会清除该参数的错误记录。连续三轮纯文字无工具也停止。
- 每轮模型请求默认上限 90 秒，可通过内部 `BrowserAgentOptions.modelTurnTimeoutMs` 覆盖；超时中止本任务，不自动换模型或重试。这是异常等待上限，不是推理提速承诺。

## 性能日志

`browser_agent.model_turn` 增加：

| 字段 | 含义 |
| --- | --- |
