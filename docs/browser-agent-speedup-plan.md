# 浏览器操作提速与卡死治理路线图

来源：2026-10-16 用户提供的真实时间日志（猎聘打招呼任务空转 7 分钟并中止）、`dsh-ai-recruiter` 与 `xinzhao` 现网代码只读分析、参考项目 `超前浏览器AI助手-v0.2.0`（Browser Agent Harness）逆向源码对照。

本文是**施工顺序**，不是完成记录。历史实现说明见 [浏览器 Agent 性能优化](browser-agent-performance.md)，执行边界见 [AI 招聘工作台](workbench.md)。

---

## 0. 一页结论

现状不是"每一步慢"，而是三件事叠加：

1. 平台预设**2 秒就退出**（职位核验门不可满足 → 死局）；
2. 退出后**全程由模型逐步试错**（实测 30–70 秒/轮，13 轮）；
3. 模型的**反空转保护 7 分钟才触发**（失败键过于敏感）。

因此分成两条独立战线：

- **A 线｜让快路径真正接管**——治"走不通"。不改变速度上限，但决定任务是否可用。
- **B 线｜让快路径本身更快**——治"慢"。把单步从 0.3–1.2s 压到 10–80ms。

**顺序：A 必须先于 B。** 当前状态是"7 分钟 0 人"，先优化单步没有意义。

**硬约束（不可突破）**：每人 ≥5 秒点击间隔（`src/lib/greeting-policy.ts:8`）、日额度。因此**整个任务永远做不到毫秒级**；能做到毫秒级的只有"单步"和"单候选人"。任何声称整任务毫秒级的方案都是错的。

## 2. 参考项目的五个杠杆（借什么、不借什么）

参考：`/Users/liuxin/code/超前浏览器AI助手-v0.2.0`（`Browser Agent Harness v0.2.0`，34 个源模块）。

| # | 杠杆 | 证据 | 我们是否借用 |
| --- | --- | --- | --- |
| L1 | **整段操作 = 一次 `Runtime.evaluate`**：流程不再是 N 步往返 | `browser_execute_js`、`run_skill_script`（`recovered/src/browser-tools/server.js`、`recovered/src/skills/server.js`） | ✅ 借形态（受控版，见阶段 4） |
| L2 | **验证过的序列沉淀成代码**，模型只决定"用哪个技能" | `save_skill` / `get_skill` / `run_skill_script`；`code` 必须是"已在页面真实跑通过" | ✅ 借（阶段 4） |
| L3 | Agent 循环与 MCP server **同进程**，`InMemoryTransport`，零 IPC | `recovered/src/background/mcp-hub.js` | ⚠️ 收益小（本地 WS 一跳仅 1–5ms），最后再说 |
| L4 | 只读工具按 `readOnlyHint` **真并发** | `recovered/src/background/agent-loop.js` | ✅ 借（阶段 4） |
| L5 | `chrome.userScripts` 在 `document_start` 预注入站点脚本 | `recovered/src/skills/injections.js` | ⚠️ 可选，收益有限 |
| — | **任意 JS 直接交给模型** | `browser_execute_js` 原样执行模型给的 code | ❌ 不借。它面向"用户自己的浏览器、后果自负"；我们要写业务系统，必须留证据链 |
| — | **无写入证据链** | 其 `browser_type` 建议"没生效就试 execute_js 直接操作" | ❌ 不借。此路径在我们的场景等于绕过业务回执，属明令禁止 |

**一句话**：借它的**执行形态**（一次 evaluate 干完整段、脚本沉淀、只读并发），保留我们的**副作用纪律**（`PageOperation`、防重、额度、未知即停、入库回执）。

### 阶段 4｜借鉴参考项目的执行形态（1–2 周，需先立项）

**前置**：先做一次真实页面耗时实测（见 4.0），用数据决定是否投入。

- **4.0 可行性实测（半天）**：在真实猎聘页面用 `Runtime.evaluate` 手写脚本跑通"开下拉 → 过滤 → 选中 → 读回选中值"，实测耗时。**若实测 >300ms 而非 20–80ms，本阶段需重新权衡。**
- **4.1 受控执行通道**：新增 `browser_run_script`，参数 `{ tabId, scriptId, args }`，**不接受模型现场传代码**。
- **4.2 托管脚本仓库**：脚本落盘 `~/.xinling-recruitment/scripts/<site>/<name>.js`，带 `sha256`、站点匹配、版本、`verifiedAt`。
- **4.3 两阶段闭环**（对应 L2）：
  ```
  [学习阶段 · 秒级，仅在首次/改版时]
    模型 + 常规 browser_* 工具摸索 → 真实跑通一次 → save_script（用户确认卡片）→ 落盘
  [执行阶段 · 毫秒级，零模型]
    预设直接调 scriptId → 返回值过宿主校验 → 推进
  ```
- **4.4 沙箱化执行**（比参考项目更严）：脚本内屏蔽 `fetch` / `XMLHttpRequest` / `WebSocket` / `chrome` / `localStorage`；只允许 DOM 读写与信任事件。
- **4.5 强制证据返回**：脚本返回值必须携带宿主可核验字段（候选人姓名原文、选中职位原文、点击目标文本、列表页码），宿主继续执行 `assertPositionEvidence` / 防重 / 额度 / 未知即停。
- **4.6 只读真并发**（L4）。
- **4.7（可选，最后）** agent loop 下沉到扩展（L3）——收益最小、改动最大。

**首批脚本只放两个**：猎聘职位切换、猎聘单人打招呼。

**验收**：单步操作 10–50ms；单候选人浏览器侧 <100ms；零模型调用。

## 4. 顺序理由

1. **0 先于 1**：没有量化就无法证明 1/2 有效，也无法判断阶段 4 是否值得投入。
2. **1 先于 2**：P0 是可用性，B 是体验。当前 7 分钟 0 人，先优化单步无意义。
3. **3 与 2 并行**：两者无耦合；3 是 2 的安全网。
4. **4 最后且需实测**：它改变执行模型与安全边界，依赖扩展新增受控 JS 通道，投入最大；必须先有实测数据。
5. **5 最后**：瓶颈不在浏览器。

## 7. 明确不做

- 不承诺整任务毫秒级（受 5 秒/人规则与服务端 I/O 限制）。
- 不把任意 JS 能力直接暴露给模型。
- 不绕过 `PageOperation`、候选人身份核验、防重、额度与入库回执。
- 不把"点击回执"当作"消息送达"，也不把 `unknown`/`pending` 记为成功。
