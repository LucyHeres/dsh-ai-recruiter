# 人才寻聘：产品形态提案

日期：2026-10-17。状态：完整产品提案；首版 0.1.115 已实现选职位、需求读取、双渠道只读寻聘、证据评分和按职位分批查看等核心流程，具体已实现范围与验证边界见 [人才寻聘说明](talent-sourcing.md)。原交互草案中的人物、履历和分数均为虚构示例。

## 1. 产品定位

在现有 AI 招聘工作台增加「人才寻聘」，以一个具体职位为中心，让 HR 完成：明确用人要求 → 在多个来源找人 → 统一阅读和比较 → 选择下一步 → 将结果回收到薪人薪事。

用户买单的结果是“更快得到一份值得联系、能说明推荐原因的候选名单”。衡量价值时关注有效候选比例、HR 阅读与筛选耗时、进入面试比例；浏览数量和发送数量仅作为过程指标。

产品主对象为「寻聘项目」：关联公司与职位，保存需求版本、渠道范围、搜索批次、候选名单和处理记录。项目能跨多次执行继续；聊天和工作台访问同一项目。现有一次性的浏览器执行任务作为项目下的执行批次。

## 2. 需求入口：选择职位 + 自然语言补充 + 可编辑标准

职位选择是入口的必需步骤。未选择职位时只展示薪人薪事的在招职位，不展示候选名单或开始按钮。每个职位的要求、寻聘批次和候选结果独立；切换职位进入该职位自己的工作区。

选定职位后，优先展示并直接使用主系统已有的职位说明和招聘要求，包含实际可读取的职责、技能、地点、经验、学历、薪资等信息。HR 无需重新输入已有内容。AI 从原文提取搜索和匹配依据；信息明确时可以不补充任何内容直接开始，仅缺失或冲突且影响执行的信息需要补充。

自然语言输入是可选补充，用来表达本轮的侧重点，例如：

> 帮我找上海的 Java 后端，做过支付或交易系统，最好负责过核心模块。预算 25–35K，可以接受能力强但年限稍短的人。

AI 生成一张可编辑的「招聘标准卡」，每项都有原文来源和优先级，不凭经验偷偷添加学历、行业或年限门槛。首次开始前由 HR 确认。

| 标准类型 | 表现形式 | 示例 | 用法 |
| --- | --- | --- | --- |
| 确认必须满足 | 必须项，可改成偏好 | Java 后端实战；上海工作 | 明确不满足时移入“条件不符”；信息不足进入“待核实” |
| 优先比较的能力 | 维度、重要程度、判断依据 | 分布式系统、支付交易、独立负责模块 | 生成有证据的匹配分和推荐原因 |
| 可协商条件 | 区间、偏好、备注 | 25–35K；年限可放宽 | 展示差距和可谈空间，不擅自变成硬门槛 |
| 搜索执行范围 | 来源、数量上限、已有候选处理 | 猎聘/BOSS；先深入看 30 人；跳过已联系 | 控制本轮搜索范围与成本 |

表达冲突时只追问影响执行的内容，例如 JD 写“必须支付经验”，补充写“交易经验也可以”，询问是否放宽。对“懂业务”“执行力强”生成可观察的待确认描述，不能当作已经可从简历证明的能力。

高级设置中才能调整具体权重。默认用户只需选择“必须 / 优先 / 加分”，避免首次使用就配置公式。

## 3. 主界面与操作流

### 职位项目列表

入口文案「人才寻聘」。展示进行中的职位、待审候选数、最近一轮状态和继续入口；一个职位可复用原项目，也可明确建立不同要求的项目，避免混用评分标准。

### 项目内工作区

顶部固定显示当前职位，可返回切换。首次进入先展示「职位要求」：主系统职位说明和招聘要求在前，可选的本轮补充在后，底部选择渠道和本轮数量并「开始寻聘」。已完成寻聘的职位默认进入候选名单，可随时回看使用的职位要求。

一次寻聘生成一个批次，保存所依据的职位要求快照、补充要求、渠道范围、候选人、匹配分和分析。完成后明确展示“本轮寻聘结果”，允许继续找一批；已有结果累计保留并去重，可按批次查看。评分始终相对于当前职位和该批次要求，跨职位不可共用分数。主系统职位要求更新时提示同步，已完成批次不被覆盖。

候选名单采用左侧列表、右侧详情：

- 列表：姓名或平台显示名、当前职位/公司、工作城市、相关经历、学历、期望薪资（可见时）、来源、初评/完整评估状态、匹配结论与最关键待核实项。
- 详情：匹配分析、完整可读履历、招聘记录。默认先展示推荐理由和证据，再展示工作/项目/教育经历；支持切换原文。已合法取得附件时提供预览，否则明确标记“仅在线履历”“仅列表摘要”“暂未取得附件”。
- 常用筛选：推荐优先看、待核实、已收藏、条件不符、已联系。分数排序必须同时展示评估范围；仅摘要初评不能混入完整评估的同一排行。
- 逐人动作：加入候选名单、不合适并选原因、稍后再看、去平台查看、选择沟通或入库。
- 选择 2–3 人后可比较：每一列对应同一条招聘标准，突出证据和信息缺口，减少反复打开简历。

候选人的评估状态（初评/完整评估/待核实）、HR 决策（待审/收藏/暂不考虑）和执行状态（待联系/结果待核对/已入库）分开保存，避免一个状态字段混淆三件事。

### 典型使用流程

1. 首先选择薪人薪事的“Java 后端”职位，带入该职位的说明和招聘要求。
2. HR 查看已有要求，可直接使用，也可选填“支付交易优先，年限可放宽”等本轮补充。
3. 选择可用平台和本轮上限，点击“开始寻聘”；系统依据该职位要求搜索、读取履历并评估。
4. 完成一轮后展示该职位的候选人、基本信息、简历、匹配度和匹配分析；执行中也可提前查看已完成记录。继续寻聘会产生下一批次。
5. HR 阅读推荐证据，收藏合适的人；对少量候选人给出“不匹配，因为没负责过核心模块”等反馈。
6. AI 提议提高“模块负责范围”的优先级；HR 确认后生成 v2，重新评估现有记录，标记需要补读的人，搜索不自动扩大。
7. HR 选择联系或入库；插件展示具体候选人与目标职位，执行既有流程并保留每人的真实结果。

## 4. 评分设计：岗位匹配度 + 信息覆盖 + 证据

分数表达“现有履历与本项目招聘标准的匹配程度”，不是一个人的通用能力分、录用概率或客观能力认证。默认用于辅助阅读与比较，由 HR 决定下一步，不因低分自动淘汰或发送拒绝消息。

先检查必须项，再对能力维度评分。明确冲突的候选人归为条件不符，必要条件缺失的归为待核实，不允许靠其他加分抵消硬性不符。

示例标准卡：Java 实战 35、分布式系统 25、支付交易 20、模块负责范围 20，合计 100。每个维度预先保存“符合/部分符合/不符合”的判断锚点：例如只列出技术关键词，证据强度低于明确的项目职责与交付结果。计算规则、权重和标准版本固定；分析保存到证据快照，不在每次打开页面时随机重评。

每条要求记录：已证实符合 / 部分符合 / 明确不符 / 未提及，以及引用的履历原文、来源和采集时间。缺失信息不得自动填满分，也不得等同于不具备。

对证据缺失的维度，以总权重为固定分母计算“已证实匹配分下限”，同时保留尚未证实的可能空间，禁止只用少量已知信息归一化成高分。硬性条件存在未知时优先展示“待核实”；仅摘要阶段优先展示初评等级，不展示与完整履历同口径的精确排行。

完整评估的示例：92/100，履历读取完整，薪资意愿待确认。维度分为 35 + 22 + 17 + 18；每个分数均可展开依据。说明“薪资意愿待确认”是协商信息，不能声称整个候选人的真实情况已验证。

列表初评与详细履历评估采用相同要求，但证据范围不同。HR 可查看得分变化缘由，例如“补读项目经历后，新增支付清结算职责证据”。同一份证据、同一标准版本得到可复用的评估结果；需求变更后保留旧版，禁止悄悄重排而不说明原因。

评分聚焦岗位职责、技能和经历，不以性别、年龄、照片等个人特征打分，不把学校名气直接当能力。历史面试结论只在当前权限范围内作为有日期的参考，不自动复刻过去的人群偏好。

## 5. 跨平台搜索与简历获取

“统一使用体验、逐个平台接入”。产品中提供所有已接入且当前用户可用的来源；没有适配、没有权限或没有登录的来源展示具体状态，不承诺搜索到所有平台的全部人才。

每个来源显示：待开始 / 搜索中 / 读取履历 / 本轮完成 / 待登录 / 待用户处理 / 暂不可用，并提供已查看与已完成评估人数。“本轮完成”只表示本轮可访问范围已处理，不代表全平台搜尽。

搜索策略分两层：

1. 把职位和招聘标准转成各平台能实际支持的关键词/条件，如 Java、后端、交易；不能设置的要求留给履历评估，向用户说明。已请求的平台筛选条件必须确认真实生效。
2. 先基于列表摘要初筛，再在数量和时间预算内读详情；先完成一小批（建议首批 10–20 人，可调整）供 HR 校准，再继续本轮范围。当前浏览器执行能力按现有锁和平台节奏运行，不把多来源界面理解成浏览器动作必然并行。

结果过少时给出“扩大关键词”“放宽经验偏好”“增加渠道”等具体建议，并说明预计影响；不擅自放松必须项。已获授权且可直接完成的同义词查询可在既定范围内执行。

跨来源身份合并先看稳定平台标识和主系统身份关联，再看已取得的联系方式等可靠证据；仅姓名/公司/经历相似时标“疑似重复”，由 HR 决定是否合并。合并后保留每条来源，冲突字段并列展示，不拼接成一份看似完全确定的新履历。

看到候选卡、看到在线履历、取得附件、获得联系方式是不同状态。联系后才可查看的信息、额度和付费限制按平台当前实际能力显示；遇到需要用户动作的情况保留已有结果并明确下一步。

## 6. 薪人薪事数据怎样发挥价值

| 数据 | 产品中的用途 | 当前接入事实 |
| --- | --- | --- |
| 在招职位、部门、工作地点、职位说明 | 预填需求，减少重复输入；以稳定职位 ID 关联项目 | 本地已有 jobList、jobDetail 操作定义；具体字段与授权返回需联调 |
| 系统职位与平台职位关联 | 避免搜索/沟通时选错同名职位 | 本地已有 jobAds 与平台职位读取 |
| 主系统人才库、已有应聘记录、联系记录 | 优先复用已有人才，提醒正在跟进或已联系，避免反复打扰 | 产品计划，需要补充查询接入；不能从现有上传/查重接口推断已经可搜索人才库 |
| 历史面试评价与明确业务反馈 | 提示需补问的问题，帮助 HR 调整本职位标准 | 后续阶段，需核对数据权限、时效与接口 |
| 简历解析及最终入库记录 | 将选中的人才交给主系统招聘流程，显示真实入库结果 | 本地已有采集/解析/提交流程；每次实际结果以最终业务回执为准 |

优先让“现有人才是否可复用、是否已经有人跟进”参与找人工作流，而不是为了使用数据做额外报表。系统里有数据不等于插件已能读取；具体接入另行核对。

## 7. 和现有插件的关系

- 工作台增加「人才寻聘」，现有「打招呼」「简历入库」继续作为快捷操作。
- 寻聘默认为只读搜索、详情阅读和本地候选整理；沟通与主系统入库从明确的候选选择发起，复用现有执行器、去重、限额和结果记录。
- 聊天可创建或补充需求、启动已确认范围内的寻聘；右侧面板显示项目进展，点击打开完整名单。浏览器轮询只读状态，不重复执行。
- 搜索中途退出保留已经评估的候选人；失败只影响对应渠道/执行批次。沟通或入库结果未知时显示“需核对”，不能借重新寻聘自动重放。
- 平台页面语义、搜索策略和评分属于招聘插件；薪招扩展继续提供通用浏览器能力。

## 8. 推荐落地顺序

### 首版：跑通“找出值得联系的人”

先接猎聘、BOSS 的实际可用搜索入口，提供职位/自然语言需求 → 标准确认 → 搜索及在线履历读取 → 有证据的初评与完整评估 → 名单/详情 → 收藏/不合适 → 交给现有沟通与入库。首版保留信息不足、平台不可用和部分完成的真实状态。

### 第二阶段：利用主系统存量，改善筛选效率

接入主系统人才库和跟进记录，增加确定/疑似重复识别、2–3 人比较、HR 反馈调整标准、已有名单重新评估，并补充新的招聘平台。

### 后续：形成持续寻聘

按用户明确设置持续找新增人选，只在出现符合标准的新增人才或需要处理时提醒；沉淀可复用的职位标准。新增平台、长期托管、自动联系规则分别提供清楚的范围设置。

首版验收重点：HR 不重复抄 JD；每条推荐能回到履历依据；可以识别未知信息；同一候选人不重复操作；部分平台失败仍可使用已有名单；选中人才后能进入现有招聘流程。评估效果由 HR 对相同候选样本校准，记录推荐被收藏、进入面试及耗时等结果，不预设未经验证的提效数字。
